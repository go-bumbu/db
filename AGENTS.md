# AGENTS.md

This file provides guidance to AI coding agents (e.g. Claude Code) when working with code in this repository.

## Commands

```bash
make test              # run fast tests with coverage (no Docker)
make test-integration  # run only the Postgres tests in Docker (integration/ module)
make test-all          # make test, then make test-integration
make lint              # run golangci-lint (must be installed externally)
make benchmark         # run benchmarks
make license-check     # check dependency licenses (needs go-licence-detector)
make verify            # run test-all + license-check + lint + benchmarks + coverage check (needs Docker)
go test ./...          # run all tests
go test ./gormdb/ -run TestOpen  # run a single test
CGO_ENABLED=1 go test ./gormdb/sqlitecgo/  # the mattn driver needs CGO
```

## Architecture

This is a Go library (`github.com/go-bumbu/db`) providing the GORM database foundation for bumbu apps. It is not an application: it is imported by other projects and never imports an app.

### Packages

- **gormdb/** — Core. `Cfg` (`SqliteCfg`, `PostgresCfg`), `Cfg.Validate`, `PostgresCfg.DSN`, `Open(cfg, Drivers)`, `Close`, `Ping(ctx, db)`, `ReaderDB(db)` (the SQLite read pool, for `DBStats`) and the `Read` / `Write` clauses (dbresolver's, re-exported so apps need not import it). Defines the `Drivers`, `SqliteDriver` and `PostgresDriver` interfaces. Imports no database driver.
- **gormdb/sqlite/** — Pure-Go SQLite driver (`glebarez/sqlite`, modernc). No CGO. Pragmas in glebarez's `_pragma=name(value)` format, `SqliteCfg.Pragmas` included.
- **gormdb/sqlitecgo/** — CGO SQLite driver (`mattn/go-sqlite3`). Needs `CGO_ENABLED=1`. Pragmas in mattn's `_busy_timeout=N` / `_foreign_keys=1` format; mattn has no DSN parameter for an arbitrary pragma, so `SqliteCfg.Pragmas` travel as `_gormdb_pragma=name(value)` and `OpenDB` runs them from a `ConnectHook` on a pool of its own (`sql.OpenDB` with a connector, no extra registered driver name). Use it for SQLite extensions such as sqlite-vec.
- **gormdb/postgres/** — Postgres driver (`gorm.io/driver/postgres`, pgx). `OpenDB` opens the pgx pool from `cfg.DSN()`; embed `Driver` and replace `OpenDB` to build the pool another way.
- **gormdb/internal/sqlitetest/** — Test suite shared by both SQLite driver packages (routing, read-only pool, WAL, pragmas, paths, error translation). Internal on purpose: the two shipped adapters are the supported `SqliteDriver` implementations.
- **gormdb/gormdbtest/** — `Sqlite(t, drv, cfg ...gormdb.Cfg)` opens a temp-file SQLite database closed on cleanup, so apps test on the same writer/reader setup they run on instead of `:memory:`. The optional `Cfg` passes the app's options (Logger, NamingStrategy, Readers, Pragmas, ...); its `Driver` and `Sqlite.Path` are overridden; a nil Logger becomes `logger.Discard`.
- **integration/** — Separate module (`replace` to `../`) with the Docker-backed Postgres tests, so testcontainers and Docker stay out of the library's `go.mod`. Not reached by `go test ./...` at the root.
- **gormdb/internal/sqliteerr/** — Maps SQLite extended result codes to gorm sentinels; both SQLite drivers call it from their `Translate` after reading the code from their own error type.

### Key Design Decisions

- **Pluggable drivers, no global registration**: the core imports no database driver; the app passes the drivers it supports in `gormdb.Drivers{Sqlite: ..., Postgres: ...}` and `Cfg.Driver` selects among them. A binary links only the databases it uses, and CGO is needed only when it imports `sqlitecgo`. A config naming a driver that was not passed makes `Open` return an error naming it. The config never chooses between glebarez and mattn; the app does.
- **Driver names and the module graph**: `gormdb/sqlite` (glebarez) registers the `database/sql` driver name `sqlite`, the same as `modernc.org/sqlite`, so a binary linking both panics at init; `gormdb/sqlitecgo` registers mattn's `sqlite3`. A binary links only the driver packages it imports, but a consumer's module graph and `go.sum` include all three drivers (glebarez, mattn, pgx), since they live in this one module. Documented in README.md.
- **Pragmas in the DSN, not `Exec`**: most pragmas are per connection, and an `Exec` hits one pooled connection only. The two drivers use different formats (glebarez `_pragma=busy_timeout(5000)`, mattn `_busy_timeout=5000`), produced by `SqliteDriver.WriterParams` / `ReaderParams`; the app's `SqliteCfg.Pragmas` are formatted by `PragmaParams` and added to both (Open merges into a new map, never the driver's, before adding `mode=ro`). The driver opens each pool (`SqliteDriver.OpenDB`), which is what lets mattn run the extra pragmas from a connect hook. `Validate` rejects pragmas the library manages (`busy_timeout`, `foreign_keys`, `journal_mode`, and `locking_mode`, which mattn sets to NORMAL on every connection), and names/values that are not a plain identifier (value: identifier or integer), so nothing can be injected into the DSN or the `PRAGMA` statement. `foreign_keys` is on so SQLite enforces foreign keys like Postgres. A file database and its readers are addressed by `file:` URIs with an escaped path, so `?`, `#` or `%` in a directory name do not break the DSN.
- **Driver contract checked at open**: each `SqliteDriver` decides its pragma policy, but `Open` verifies on the writer that `journal_mode` is WAL (file databases) and `foreign_keys` is on, and fails with an error naming the `SqliteDriver` contract otherwise. `gormdb/sqlite` and `gormdb/sqlitecgo` are the supported implementations; the behaviour suite stays in `internal/`.
- **Writer/reader split for SQLite** (`gormdb/sqlite.go`): one write connection (`SetMaxOpenConns(1)`, WAL, checked at open) plus a read-only pool (`mode=ro`, `SqliteCfg.Readers`, default 10) registered with `dbresolver`. Writers queue in Go instead of hitting `SQLITE_BUSY` (within the process; another process on the same file can still exceed `busy_timeout`); WAL lets reads run while a write is in progress. See the benchmark at https://github.com/andresbott/gorm-sqlite-concurrency. In-memory databases fall back to one connection. `Close` closes both pools: they are held by a small GORM plugin (`sqlitePools`, in `db.Plugins`), so there is no global state.
- **Routing contract** (documented on `Open`), stated by intent: a plain SELECT goes to the read pool, everything else to the writer, by SQL text rather than by method (GORM-built queries and raw SQL from `Raw` and `Exec` alike); `Clauses(gormdb.Read)` / `Clauses(gormdb.Write)` force either; inside `db.Transaction` and `db.Connection` everything stays on the connection they hold (the `sqlitePools` plugin wraps dbresolver's callbacks to skip a pinned `*sql.Conn`, which dbresolver would otherwise swap back to a pool and deadlock on). How a plain SELECT is told apart (longer than 10 characters, not ending in `FOR UPDATE`, no `FOR` clause; `WITH ...` and `PRAGMA` go to the writer) is dbresolver's behaviour at the tested version, documented as such, not a gormdb promise. On a file database the `gorm:db_resolver` plugin slot is taken, so an app's own `dbresolver.Register` returns `gorm.ErrRegistered` (suite: `own resolver rejected`). Reads wait for a free reader, so more concurrent reads than `Readers` queue in Go. SQL that depends on the connection (`SELECT last_insert_rowid()`, `changes()`, temp tables) needs a transaction or `db.Connection`, since a bare SELECT lands on a read-only connection (`gormdb.Write` reaches the writer, but another goroutine may write in between). `db.DB()` is the writer pool: its limits must not be changed. `ReaderDB` exposes the read pool for stats only; `Ping` pings one connection of each pool.
- **Tested GORM / dbresolver versions and the Open-time check**: the library is tested against `gorm.io/gorm v1.31.2` and `gorm.io/plugin/dbresolver v1.6.2` (the versions in `go.mod`; update this line when bumping them). The pinned-connection wrapper relies on dbresolver's callback name (`gorm:db_resolver`), its six processors, and GORM running a `Before("*")` replacement in place of the original. A consumer whose module graph selects other versions gets `checkPinning` (`gormdb/sqlitepools.go`) as the guard: at `Open` it runs each processor's compiled callbacks in dry-run mode, with an error preset so GORM's own callbacks do nothing, on a statement pinned to a writer `*sql.Conn`, and fails `Open` with an error naming the processors and the linked versions if any moved it off; a control first checks that an unpinned query does move to the read pool, so a GORM that stopped running callbacks there fails rather than passes. After bumping GORM or dbresolver, also run the suite's `connection stays pinned` and `quiet open` tests.
- **Deadlock caveat**: inside `db.Transaction` or `db.Connection`, use only `tx`. The single writer connection is held by the callback, so any statement on `db` that reaches the writer (Exec, WITH, PRAGMA, short SELECTs, `gormdb.Write`) waits forever. For `:memory:` (one connection for everything) any statement on `db` inside the callback hangs, reads included, and so does a write while query rows are open, although the same code works on a file database; apps should test on a temp file (`gormdbtest.Sqlite`).
- **`_txlock=immediate`**: a transaction takes the write lock at `BEGIN`, so a read-then-write transaction waits (honouring `busy_timeout`) instead of failing with `SQLITE_BUSY` on upgrade. Set for the writer on both SQLite drivers.
- **glebarez vs mattn**: glebarez (modernc) is the no-CGO option, but per the benchmark above it writes roughly 100x slower than mattn in WAL mode (about 197 vs 20,000 writes/s). It is not "the default"; choose `sqlitecgo` when write throughput or extensions matter and CGO is acceptable.
- **Error translation**: `Open` always sets `TranslateError: true`. The SQLite drivers wrap the upstream dialector's `Translate` to also map constraint errors (unique, primary key, foreign key, CHECK) to gorm sentinels while keeping the original driver error. Callers check with `errors.Is(err, gorm.ErrDuplicatedKey)` / `errors.Is(err, gorm.ErrForeignKeyViolated)`, never by string matching. There is no separate `dberr` package.
- **Postgres DSN**: built as a URL, so user, password and database name are escaped; port defaults to 5432; `sslmode` defaults to `require`; an empty user is left out of the URL (a password then goes in the `password` query parameter); query spaces are `%20`, never `+`, which libpq keeps literally; `connect_timeout` defaults to 10s so `Open` fails fast; `Params` adds parameters but cannot repeat a field's; pool settings are applied to the pool before `gorm.Open`. `Validate` rejects a host with a port, a port out of range, an unknown `sslmode` and negative durations. `PostgresCfg` redacts `Password` and every `Params` value (keys stay visible; a blanket rule, since `sslpassword` and others can hold secrets) in `String` and `LogValue`. A failed `gorm.Open` (failed ping included) closes the pool itself from GORM v1.31.2, which `go.mod` (and `gorm.io/driver/postgres` >= v1.6.2) requires; `TestFailedOpenClosesPool` guards it.
- **The driver opens the pool, the core owns it** (both databases): `PostgresDriver.OpenDB(cfg PostgresCfg)` returns the pool and `Dialector(conn)` wraps it, the same shape as `SqliteDriver`. `openPostgres` applies the pool settings before `gorm.Open` and closes the pool itself if opening fails, so cleanup does not depend on the GORM version. The shipped driver connects with `cfg.DSN()` (`sql.Open("pgx", ...)`); an app that must build the pool itself (rotating credentials such as IAM tokens, a tracing wrapper) embeds `postgres.Driver` and replaces `OpenDB`, reading the validated `PostgresCfg` fields instead of parsing a DSN. `Validate` does not require a password, so such a driver needs no dummy values.
- **SQLite path**: `SqliteCfg.Path` is a filesystem path or `:memory:`; `Validate` rejects a `file:` URI (both drivers would silently create a file with that name). `Open` resolves a file path to an absolute one once (`filepath.Abs`, which also cleans it) and builds the writer and reader DSNs from it: connections open lazily, so a relative path would otherwise follow a later `os.Chdir` (readers failing, a reconnecting writer creating a new empty database; suite: `chdir after open`). `fileDSN` cleans the path so a leading `//` is not read as a URI authority, and keeps a path that cleans to `:memory:` (e.g. `./:memory:`) a file. `BusyTimeout` must not be negative; it is kept between 1ms and 2^31-1 ms, since SQLite turns waiting off for 0 and for a value it cannot store. A failed `Open` removes the directories it created.
- **Constructor convention**: configuration goes through one `Cfg` struct, like the other bumbu libraries. Code-only options on `Cfg` (`Logger`, `NamingStrategy`, `NowFunc`, `SkipDefaultTransaction`) pass straight to `gorm.Config`. `PrepareStmt` is deliberately not offered: it interacts with dbresolver's prepared-statement store and the pinned-connection wrapper, an untested combination.
- **WAL caveats**: WAL does not work on network filesystems, and copying a database file needs its `-wal` file (or close the database first). `Close` closes the readers, waits (up to 5s) for reads still running, then closes the writer, so the writer can checkpoint and remove the `-wal` file; concurrent and repeated calls are serialised; reads still open after the wait (rows never closed) make `Close` return an error; always release through `gormdb.Close`, not `db.DB().Close()`.

## Linting
